# v1.3.11 paired performance contract

All automatic release decisions compare the final candidate with immutable baseline
`bb4f1a7e90db1fdfd785936594d080e8c4a0ba4e`. Measurements use at least ten predetermined,
counterbalanced pairs, identical logical datasets/configuration/JDK/native libraries,
and a fresh subprocess for every side of every pair. Performance processes run serially
on dedicated hardware.

For ordinary ratio metrics, reports contain the paired geometric-mean candidate/baseline
ratio and a two-sided Student-t 95% confidence interval computed in log space. Automatic
acceptance requires both:

- the point estimate is at least 1.0 for throughput or at most 1.0 for cost metrics;
- the confidence interval does not demonstrate a regression (throughput upper bound is
  at least 1.0; cost lower bound is at most 1.0).

In addition, at least one predeclared primary metric must demonstrate a material gain:
throughput lower 95% at least 1.02, or latency/CPU/allocation/memory upper 95% at most
0.98. Allocation, GC, threads, native handles, and parked/outstanding resources have no
exception path. GC/resource counters use exact per-pair no-increase checks, including
zero-valued samples that cannot form a log ratio.

The 0.99 throughput and 1.02 latency/CPU/memory values are exception ceilings only.
`exception_candidates` never changes `passed` to true. An exception still requires exact
commit ablation, causal and bounded correctness/resource justification, profiles proving
no cheaper implementation, a material compensating gain in the affected workload, full
hardware/provenance evidence, and explicit user approval before integration or release.

## Report schemas

The machine-readable schemas are versioned and checked in under `benchmarks/schemas/`:

- `rockserver-grpc-raw-scan-comparison-v3` records all ten raw worker pairs, absolute
  throughput/latency/process/resource measurements, ratios/intervals, material gains,
  exception candidates, correctness/conservation/drain fields, and failures.
- `rockserver-grpc-retained-read-comparison-v2` records the fixed eight-scenario matrix,
  strict worker provenance, absolute values, process/resource telemetry, per-scenario
  ratios/intervals, material gains, exception candidates, and failures.
- `rockserver-seven-profile-paired-comparison-v1` records the immutable schedule
  provenance, all absolute paired vectors, ratios/intervals for every profile and global
  process/resource metric, classpath/production/native/JDK/hardware fingerprints,
  material gains, exception candidates, and failures.
- `rockserver-performance-exception-v1` is a separate evidence record for the exceptional
  path. It requires the failed automatic result, exact ablation commits, bounded causal
  explanation, alternative profiles and hashes, a material compensating gain, hardware
  metadata, and an explicit user-approval reference. Creating this record never changes
  the automatic result's `passed=false` value.

Raw and retained controllers write their reports directly. Seven-profile workers first
write strict `rockserver-seven-profile-pareto-worker-v1` property artifacts; the paired
controller rejects missing, unknown, duplicate, empty, non-finite, or provenance-drifted
fields before producing its comparison report.

Structural smoke runs validate parsing and process compatibility only. They are not
performance evidence, even when every structural check passes.

## Scheduler hot-path gate

Compile the final candidate test harness once and compile production classes in both
the immutable baseline and candidate worktrees. Keep the candidate test classes first
and select only the production `target/classes` entry between runs:

```bash
mvn -q -DskipTests test-compile dependency:build-classpath \
  -Dmdep.outputFile=target/scheduler-hot-path.classpath

deps="$(<target/scheduler-hot-path.classpath)"
harness="/tmp/rockserver-v131-scheduler-integration/target/test-classes"
main="it.cavallium.rockserver.core.impl.benchmark.SchedulerHotPathBenchmark"
baseline_cp="${harness}:/tmp/rockserver-v131-perf-baseline/target/classes:${deps}"
candidate_cp="${harness}:/tmp/rockserver-v131-scheduler-integration/target/classes:${deps}"
```

Run `normal`, `indexed`, `cooperative`, `cooperative-yield`,
`cooperative-park-resume`, and `cooperative-cancel` in fresh, serial,
counterbalanced baseline/candidate subprocess pairs. The second and third arguments
are warm-up and measured operation counts. Admission/dispatch/cancellation report
throughput and submitting-plus-worker allocation per operation. The repeated YIELD
and PARK/resume cases reuse already admitted scheduler nodes, keep end-of-window
coordination outside the measurement, and fail the process unless both measured
threads allocate exactly zero bytes after warm-up. The harness uses optional snapshot
accessors so the unchanged candidate test classes remain binary-compatible with
baseline `bb4f1a7` production classes.
