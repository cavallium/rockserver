# Distributed Rockserver: range replication without discarding the LSM

Design decision, 2026-10-07. This document specifies a proposed implementation; it does not describe a working distributed release. Rockserver baseline: `c431f88884a6735ff25f4538377d811fb2ea7832`, branch `master`, `/home/cavallium/IdeaProjects/rockserver`. The checkout contains unrelated changes; all architecture evidence below comes from committed source. No builds, repository modifications, production reads, or deployments were performed for this design.

## Decision

Build a shared-nothing, range-partitioned database around the existing RocksDB engine. Each range is an independent Raft group, implemented with **Apache Ratis 3.3.1**, with three durable voting replicas by default. Preserve native column families, compact merge operands, ordered keys, block caches, compression, tier placement and workload profiles. Keep the standalone implementation available. Add a distributed backend and client routing layer; do not make `EmbeddedDB` pretend that its local handles and RocksDB sequence numbers are cluster-wide identifiers.

The common write is one bounded logical command, one quorum replication round, and one local atomic RocksDB apply. Independent commands are batched and pipelined. No global timestamp service or per-write metadata quorum is on this path. Reads are linearizable by default. An explicit weaker read mode can use a sufficiently caught-up follower. Native merge callbacks remain deferred inside RocksDB, so sparse updates do not become full-value replication.

Cross-column transactions remain supported. Colocate keys where the application has a natural common prefix; use a replicated two-phase commit decision for transactions spanning groups. Unprepared write transactions and their native snapshots are **leader-term-bound**. Leadership loss returns a retryable whole-transaction error; a submitted commit instead has a durable, queryable outcome. This avoids imposing permanent application-level MVCC or a persistent version record on every tiny key. Local transaction conflict detection uses a bounded in-memory mutation history, including ABA and range changes. Prepared locks and decisions, which must survive failures, are durable.

Use a few RocksDB **storage pools** per node, usually separated by NUMA locality and materially different storage/SLO requirements. Many ranges share a pool and a logical column's CF; a range is not a new RocksDB instance or a new CF. A transaction confined to one group always applies within one pool. All groups share bounded transport and execution resources where the library allows it; measure Ratis's remaining per-group overhead and constrain placement accordingly.

Initially keep RocksDB's local WAL enabled with `sync=false`, in addition to the synchronously replicated Raft log. This is **two local log writes, one durability barrier**, not a single-log design. The duplication buys established cross-CF crash recovery and keeps the implementation auditable. Removing the local WAL requires a separate, proven atomic-flush recovery mode and demonstrated benefit; it is not a launch requirement or a hidden default.

The recommended architecture is a defensible fit for this code and hardware class, not a claim of a globally optimal database. The main performance risks are real: Raft replication bandwidth and fsync, per-group Ratis overhead, conflict tracking under sustained transactions, snapshot/migration I/O, three copies of compaction work, and write interference between CFs sharing a pool. Final acceptance measures these explicitly.

## 1. Namespace, routing and physical layout

### Logical identity and ordering

Introduce stable `clusterId`, `databaseId`, `columnId`, `schemaEpoch`, `rangeId`, `rangeEpoch`, `replicaId` and `nodeIncarnation`. None are RocksDB CF handles, endpoints, process IDs or Raft leader terms. Keep RocksDB handles local. Use immutable binary encodings and unsigned bytewise comparison matching the existing `calculateKey` result. Test negative signed logical IDs through their existing encodings; do not reinterpret them to make ranges look positive.

A **partition domain** specifies columns, an order-preserving routing projection, and placement/storage policy. Default for a newly distributed column: routing key = its complete existing physical key, with range boundaries on that key. Optional colocated domains use the same immutable leading fixed-key prefix across named columns. Validate prefix width/encoding at schema creation. All records with that routing prefix remain together, making related cross-column updates one-group operations. Do not invent an implicit hash for general-purpose range columns.

Hash partitioning is an explicit policy for point-only domains, not the default. It scatters ordered scans and prevents cheap first/last operations. A hot unsplittable colocation prefix is a measurable limit: split the application's prefix policy through an explicit migration, or accept the hotspot; do not silently break transaction colocation. The routing function and physical key codec are schema data with content hashes and epochs.

A range descriptor contains `[lowerInclusive, upperExclusive)`, domain/schema epoch, group ID, current configuration version, replica/node identities, placement requirements and topology state. Cached clients binary-search the map and send directly to the leader. A wrong/stale route returns a typed descriptor update. One optional server forwarding hop is permitted for stale routing caches; it consumes the original deadline and never changes a mutation's identity. There is no mandatory gateway hop or catalogue RPC for ordinary operations.

### Shared storage pools

Within a storage pool, keep one native CF per logical column/operator/options combination, and a few internal CFs for replica state, durable receipts, prepared transactions/locks and topology state. Keep original user key bytes in user CFs. Range boundaries are ownership intervals over those keys, not per-range prefixes that force key rewriting on every split. Different databases/columns get distinct CF identities; no concatenation ambiguity is allowed.

One node may host only one active replica owner of a given database/column/key interval in a pool. Incoming replicas install only into inactive, fenced intervals. A split can transfer two disjoint subranges to child groups in the same pool without rewriting user keys. Merge is the inverse. Retired ownership is a durable tombstone, not deletion of user rows while children still reference them. Node-wide ownership validation prevents stale import or cleanup from affecting another active range.

Sharing amortizes memtables, caches, metadata and compaction, but a RocksDB write stall can affect other CFs in that DB. Put incompatible latency/archive workloads into distinct pools. Do not create a pool per range. Groups that must atomically update multiple CFs must place those CFs in the same pool on each replica; if their policies require different pools, use the cross-group protocol even when physically cohosted.

Range size is a placement control, not a fixed architectural constant. Start calibration with a small number of ranges and sweep size/density. Use compressed bytes, mutation rate, foreground latency, compaction debt and transfer time to select splits. Require hysteresis and minimum lifetime before merges. Ratis has per-group work, so cap admitted groups using measured threads, native/heap memory and idle CPU. A dense-shard benchmark is a release gate; millions of tiny Ratis groups are not a supported assumption.

## 2. Replication and the durable write path

### Why Ratis, and exactly what it provides

Ratis is a maintained Java Raft library, with 3.3.1 announced on 2026-09-22 and 3.3.0 on 2026-08-12. The project reports testing with Ozone/IoTDB. The choice keeps consensus inside Rockserver's JVM and uses a released implementation for election, log repair, membership changes and snapshots. It does not supply Rockserver transactions, deduplication, safe apply, placement, or resource isolation automatically. [R1–R4]

Pin 3.3.1 and its dependency graph in the implementation; verify checksums, license, supported JDK, shaded protobuf/gRPC and Netty compatibility against the exact Rockserver build. Do not downgrade Rockserver's JNI or replace the consensus implementation midway without a recorded correctness/performance reason. SOFA-JRaft and Rust implementations are credible alternatives, not automatically faster choices. Ratis's measured density/throughput is an explicit early go/no-go before broad implementation.

Use the Ratis `StateMachine` contract directly. Its asynchronous `applyTransaction` callbacks may overlap despite ordered invocation: Rockserver supplies ordered per-group apply lanes and advances a contiguous **completed** apply watermark only after storage and result publication are ready. Never equate scheduled callback index with applied state. The upstream defaults use `Read.Option.DEFAULT`; set **LINEARIZABLE** explicitly. Disable unsafe flush and initially disable leader-lease reads. Keep actual log fsync completion in the durable acknowledgement path. [R3–R4]

Initial replication is three full voters across three independent node failure domains; quorum is two. All voters persist the command and required external data before counting toward a successful write. One failed node or a minority partition does not allow another independent writer. Operators can choose five voters for a different failure budget. Do not market three containers sharing a disk/host as three failure domains. Learners and analytical replicas do not count for write durability.

### Command and apply

The canonical log envelope includes format version, group/epoch, operation identity, schema/operator digests, command kind, ordered logical mutations and any deterministic result-plan fields. The client/leader supplies timestamps, generated IDs and randomness as explicit data **before** consensus where needed. Request deadlines determine admission/cancellation, not whether an already-committed log command takes effect during replay.

For each group, define `C` = committed index, `A` = largest contiguous locally applied index, `D` = largest index covered by a durable installable snapshot. Always `D <= A <= C` for exposed committed state. Ratis configuration/no-op entries must also advance the adapter's contiguous accounting in the correct order.

Application of entry `(term,index)` is one native `WriteBatch` containing:

1. all affected user-CF writes/merge operands/tombstones;
2. corresponding durable receipt and returned outcome, if any;
3. prepared/decision/lock metadata changes when applicable;
4. this group's applied `(term,index)` and logical-state format version.

Use RocksDB WAL enabled, `sync=false`. Do not call the existing ordinary `EmbeddedDB.put()` independently and then store the index: extract a small internal apply interface that can write the complete batch. Do not persist native transaction objects or Java callbacks in the log. There is one ordered apply owner per group; batches from independent groups can use shared pool group commit while preserving each group's order. Cross-group native co-batching is a storage optimization, never a new distributed atomicity promise.

After Ratis has a durable quorum, the leader applies and returns the saved outcome. A follower that cannot apply a committed entry stops serving that range and repairs; it does not skip the entry or advance `A`. Application validation errors are canonical result codes. Missing operator artifacts, corrupt commands or unexpected native storage failures are replica health failures. The returned mutation success means quorum durability plus local visibility, not every follower has applied.

### WAL duplication and recovery proof

Raft's durable log is the recovery authority for accepted commands. The local RocksDB WAL provides atomic recovery across CFs even if metadata and data memtables flush at different times. After restart, recover RocksDB, read each persisted `A`, check it against the group lineage, snapshot and retained Raft log, then replay committed entries strictly greater than `A`. Never replay a non-idempotent merge at or below `A`. If storage has lost a suffix, replay it; if its marker or data cannot be reconciled, fence and reinstall rather than guessing.

Raft log truncation uses only a completed, checksummed, fsynced snapshot manifest with directory durability and all included files. `getLatestSnapshot()` must not advertise a half-exported image. `takeSnapshot()` reports only a proven completed image at its actual index; background export can prepare it so a large snapshot does not stall the apply thread. `A` in a recovered RocksDB instance is not by itself permission to purge the Raft log.

The optional future no-local-WAL mode requires `atomic_flush=true`, all relevant user/internal CFs participating in every persistence boundary, tracking every auto/manual flush and schema change, crash-safe manifest/index recovery, and a log retention rule proven against flush completion. A data/metadata `WriteBatch` alone is insufficient. Atomic flush also couples all CFs and may create small SSTs or burst I/O. The initial implementation keeps the local WAL until power-loss tests and a paired workload show a net benefit from its removal. [S1]

### Replay idempotency and uncertainty

Every mutation, including merge, commit, admin operation and bulk chunk, has `(sessionId, sessionEpoch, sequence)` plus an immutable payload hash. Reusing an identity with a different payload is an error. Durable receipts migrate with the affected range and contain the original result, including previous value/delta or conflict. A retry returns that result, never the value that happens to exist now. Ratis's default 60-second in-memory retry cache is not this contract. [R3, P3]

Sessions declare bounded outstanding sequences. Client acknowledgements permit a replicated contiguous receipt-GC watermark; GC cannot make an old identity executable again. Expiring a session is itself replicated and leaves a fencing epoch/tombstone. Requests from expired epochs return `SESSION_EXPIRED`, not fresh execution. Bound unacknowledged result bytes and stop admitting more before retention exhausts disk/memory. Piggyback acknowledgements and batch identities to amortize the overhead on tiny writes. Session tombstones are not an unbounded permanent table: catalogue-issued session epochs have finite lifetimes, and a range may remove old epoch records only after persisting a coarser epoch floor that rejects every request from those epochs. Replicas that have not installed that floor retain the old receipts. Snapshots, splits and restores preserve/advance these fences; a wall-clock rollback cannot reactivate an old epoch.

Timeout after admission is **outcome unknown** until `getOperationStatus`/`getTransactionStatus` or retry with the same identity resolves it. No library automatically retries a merge with a new identity. Closing a connection or cancelling a future does not roll back a committed command. A definitively rejected, never-admitted request may be retried according to its typed error. Bounded retry/backoff belongs in one client layer.

## 3. Merge, bucket and state-dependent mutation semantics

Replicate native merge **operands**, not materialized full values, for ordinary merges. Preserve operand order. Commutativity is not required and is not assumed. Partial merge must preserve full-merge semantics under any permitted grouping/compaction schedule; if this law cannot be established, disable partial merge for that operator rather than reorder operands. Native callback inputs remain borrowed until callback return.

A distributed operator is immutable and identified by `(name, version, artifact SHA-256, class, value/operand codec version)`. Stage and verify the exact artifact on eligible replicas before activating the schema. New replicas cannot serve or become an eligible replacement without all required operators. Never resolve “latest” during apply/recovery. These identities protect the interpretation of data and retained operands. Reject mismatched artifacts; do not add support for unused historical operator formats during unreleased development.

Require a pure, deterministic, thread-safe operator: no wall clock, randomness, host locale, external I/O, mutable global state or environment-sensitive encoding. Standardize byte order, overflow and malformed-operand behavior. Property tests generate operand sequences, compaction grouping and replay schedules across independent JVMs. These tests are evidence, not proof that arbitrary Java is sandboxed or deterministic. Only admitted operators are supported in distributed mode; reject an unqualified upload with `OPERATOR_NOT_DISTRIBUTED_SAFE`. Fix/adapt the clock-reading example in a separate clearly reviewed change before using it in acceptance.

`mergeGetMerged`, `putGetPrevious`, deltas, changed/presence returns and conditional bucket updates are evaluated in the group's ordered state, and their exact result is part of the receipt. A retry cannot recalculate the previous state. For transaction staging, merge effects/read-your-writes can be computed using the same pinned implementation; final accepted mutations remain operands where safe. Do not turn every merge into an unconditional replacement merely to simplify replication.

A variable-key bucket is one physical conflict/ownership unit. No split boundary cuts it; read-modify-write of bucket contents is atomic in the apply batch. Complete-bucket consumers must receive all bucket contents within their declared budget or an explicit overload error. A physical bucket may contain multiple logical keys with shared hash; collisions must not alias application identity.

`ensure`/write elision is allowed only after ordered state validation. An elided write has no mutation-history stamp, but still has a receipt so a delayed retry cannot recreate data deleted after the original operation. Do not assume syntactic idempotence makes an operation safe to replay later in a different history.

## 4. Transactions: preserve atomicity without global per-key MVCC

### Scope and compatibility

Add `openTransaction(scope, options)` and `executeAtomic(mutations, predicates)` to the distributed API. Scope is a set of columns plus physical keys/ranges, or a declared colocation prefix. It is immutable after the first read; accessing outside it fails before that access has effects. The fast path covers one group and one native snapshot. A transaction spanning groups captures a consistent scoped snapshot as specified below. Bounds cover participants, bytes, read/write/predicate footprint, lifetime and staged response data; defaults are tunable and published in capabilities.

The existing unknown-scope `openTransaction(ttl)` remains a **database-scoped** compatibility operation. It captures all current ranges/columns and can be expensive. If the declared maximum scope cannot cover the database, return `TX_SCOPE_REQUIRED` before allocating a partially usable transaction. Never lazily take unrelated per-shard snapshots and call them the original database snapshot. Adapt the identified Yotsuba callers to explicit scope in their own authorized consumer change; a Rockserver-only implementation provides compatibility/tests without editing Yotsuba by implication.

Distributed write transactions use snapshot reads, read-your-writes and serializable commit validation. Track all read keys, absence predicates, written keys and range predicates, including migration fences and whole physical buckets. This is deliberately at least as conservative as existing optimistic conflicts. Preserve ABA detection: writing `A -> B -> A` after the snapshot conflicts even if final bytes match. No validation solely by value equality.

### Efficient, term-bound conflict history

On a leader's native snapshot capture, atomically register a transaction pin with applied index `s` in the shard apply/proposal coordination domain. Retain a bounded in-memory index of actual mutations newer than the oldest pin: latest write index per physical key, delete markers, interval tombstones, and schema/topology changes. Index range predicates with an ordered/interval structure; a hash table alone cannot detect phantoms. Conservatively invalidating a whole shard after a range delete is a safe initial implementation, with the false-abort cost measured.

All mutation paths update this index after apply, including merge, multi/batch, ingest, deleteRange and final transaction effects. A collision bucket shares one stamp. Do not discard deletes while any live snapshot could have observed the prior absence/value. Track the history's byte bound separately from transaction count; if retaining more history would exceed it, abort the oldest **unprepared** handles explicitly, release their pins, and reclaim. An invalidated transaction cannot later prepare. No O(number of stored keys) version CF is required.

Native RocksDB snapshot/iterator retention supplies old values, so there is no timestamp suffix on every user key and no second MVCC LSM. The existing Java transaction commit cannot serve as a replica-wide conflict oracle: native conflict-cache/flush behavior and process handles are not replicated state. Use the explicit history for the distributed contract. Reuse native snapshots and write-batch facilities, not a speculative local commit before quorum.

Unprepared handle identity includes group leadership generation and owner incarnation. Leadership loss/restart invalidates its writable handles; return `TX_LEADER_CHANGED` or `TX_EXPIRED`, and the caller retries the entire transaction. This is distinct from a **submitted** prepare/commit, whose identity and durable status resolve uncertainty. There is no requirement to rebuild ephemeral history after a crash. Read-only snapshot cursors have their own explicit pin-loss behavior below.

### Ordered validation without an RTT bottleneck

Every proposed mutation registers a complete physical write footprint before entering Ratis. A short ordered `ProposalLane` owns reservations, operation identity and schema/term checks. It is not an executor per key and never holds a Java monitor across native work, disk or network waits.

For commit/prepare, reserve the transaction's complete read/write/range footprint against new conflicting proposals. Check existing in-flight footprints. If they overlap, wait for their ordered outcome/apply or return conflict; if they are disjoint, they do not force a drain. Validate the in-memory history against `s`, the live native snapshot handle, durable prepared locks, current schema/epoch and the staged plan. Then append `COMMIT_ACCEPTED` for a one-group transaction or `PREPARE_ACCEPTED` for a participant. The accepted record contains the exact plan, outcome inputs, snapshot/term audit identity and scope, not a callback to rerun later.

Keep its reservation until apply installs effects or durable locks, or Ratis definitively rejects/truncates it. An uncertain append retains ownership/status. Followers apply the leader's canonical accepted plan and lock transitions; they do **not** re-run volatile conflict validation. This is safe because every potentially conflicting predecessor has applied before validation and every potentially conflicting successor is held behind the reservation. Consensus fixes the position of the accepted plan. Disjoint proposals can remain in flight, be validated in batches and share a log append/fsync.

On new leadership, complete a current-term quorum barrier, apply its entire preceding committed log, recover durable locks, and rebuild pending-admission state before serving. Do not enable admissions merely because an election callback fired. An old leader cannot finish a new accepted plan without quorum; a previously accepted plan that is retained in the new committed prefix applies before new admissions. There is no window where an inherited prepare is unknown to the new leader's conflict checks.

The first correctness milestone may use whole-shard drain-to-applied, but the final release must use disjoint reservations/pipelining. Otherwise throughput is approximately bounded by `batchSize / quorumRoundTrip` per group even when CPU/storage are idle. The final benchmark must expose this ablation rather than hide it by adding more shards.

### Durable multi-group commit

Store transaction decisions in replicated **transaction-status ranges**, sharded by transaction ID and cached by routers. They are data-plane Raft groups in a protected storage pool, not the single catalogue group. Start with a few and expand from measured load. A status range can relocate without changing transaction identity; do not split one while it contains unresolved decisions unless that handoff protocol is implemented. Single-group atomic operations bypass this service.

Protocol:

1. The coordinator freezes the participant list, schema/epoch, operation ID and plan hash, then durably writes `PREPARING` in the home status range. Participants never accept a plan inconsistent with this record. Participant registration cannot race the final decision.
2. Each leader validates/reserves as above. Its committed `PREPARE_ACCEPTED` installs the staged write plan, any result data, exclusive write locks and read/predicate validation locks in the same batch as its applied index. Only now is it prepared. Prepare is idempotent. Conflict produces an explicit negative vote; it is not a transient success.
3. After all participants durably prepare, the home group commits one immutable `COMMIT` decision. Otherwise it commits `ABORT`. Competing recovery coordinators use the same compare-and-set state transition. `COMMIT` and `ABORT` can never both be chosen.
4. Participants verify the home decision through a linearizable read or a trusted cached committed decision, then propose `FINALIZE`. On COMMIT, apply all local mutations and receipt data and release locks in one batch. On ABORT, remove staged state and locks atomically. A participant cannot unilaterally abort a prepared transaction because a client lease/timer expired.
5. Return success after the COMMIT decision and every participant's finalization is acknowledged applied. A faster decision-only future may exist as an explicit advanced API, but is not ordinary `closeTransaction(true)` success. Lost replies are resolved by status, never by executing a new transaction automatically. Retain the decision until every registered participant has durably acknowledged finalization and the client outcome/receipt GC rules permit removal; an unresolved participant must never encounter a forgotten home decision.

No shared clock establishes correctness. A timeout permits a recovery coordinator to **propose ABORT at the home group while still PREPARING**; it cannot overturn COMMIT. A slow participant that prepares after an ABORT decision is cleaned by ABORT and cannot make the transaction committed. Before sending PREPARE, the coordinator identity/plan must already be registered durably, allowing cleanup to find all possible participants.

Use no-wait/retry for incompatible prepares initially, with deterministic participant ordering and bounded jittered full-transaction retries. Do not hold a worker thread waiting for another transaction. This avoids distributed wait-for cycles without inventing a clock-based priority service. Protect decision/finalization traffic from the admission limits of user data that it must unblock.

### Visibility and serialization argument

Prepared writes are invisible in user CFs. A current-state point read, conditional mutation, or new iterator/page snapshot encountering a conflicting prepared lock must wait/help resolve the home decision and finalize locally before proceeding. It cannot return the pre-transaction value after learning COMMIT, nor read staged data before COMMIT. Once one participant has exposed a committed write, another participant's remaining lock prevents an observer from reading an old value there. Multi-key reads requiring one atomic view use the scoped snapshot protocol rather than unrelated point reads. A valid already-captured immutable snapshot reads its historical cut and ignores locks installed after that cut; resolving a newer lock must never substitute latest data into that snapshot.

The serial order of one-group commits is their accepted log order. For multi-group commits, each participant validates against every observed key/predicate and holds conflicting locks from validation through the chosen decision/finalization. Therefore no conflicting operation can interpose after validation; all read dependencies remain valid at the common decision. Read predicates include absence and ranges, so write skew and phantoms do not escape through untracked reads. Independent reads in separate API calls can straddle a commit, as they can on a single database; an explicit multi-read/snapshot cannot return a fractured transaction.

Term-bound unprepared aborts do not release durable prepared locks. A participant restart replays them before reads. Membership changes preserve the same group state; a new learner cannot vote/serve until that state is installed. Topology split/merge waits for prepared transactions and writable snapshots to drain or abort through their proper protocol.

## 5. Strong reads, snapshots and ordered cursors

Point reads use Ratis ReadIndex/quorum validation and then wait until the local completed apply watermark covers that read index. Take the native read/snapshot only after the barrier, and check prepared-lock visibility. ReadIndex requests can be coalesced with a bounded latency budget; an arbitrary cached successful heartbeat is not a linearizable lease. Do not enable time-based leader/follower lease reads without a separate clock and pause-safety analysis. A follower can serve a strong read with a valid leader-issued read index after applying it.

An optional `STALE_AT_LEAST(position)` read advertises exactly the per-range position it has applied. It remains explicit; a lagging follower does not claim a wall-clock staleness bound from its local clock. Cross-group transactions require either their complete snapshot/decision protocol or a documented weaker mode; stale range reads are never silently substituted during failure.

### Consistent snapshots without timestamped user keys

Single-group snapshots use a linearizable read barrier, reserve the scoped footprint against new prepares, resolve/finalize every already-prepared transaction intersecting that scope, and then capture the local native snapshot before releasing the reservation. This also handles a decision committed at another group before this read began. Do not capture old native data first and later mix it with values obtained while helping a committed transaction. Multi-group read/write transaction snapshots and strict cross-range read snapshots use this finite protocol:

1. Fix and pin the scope's range-directory generation; record a recoverable snapshot-fence operation and its complete participants.
2. Install each replicated write gate **through the same ProposalLane/reservation order as mutations and prepares**. First reserve the scope, preventing later conflicting admissions; then drain all pre-gate conflicting in-flight reservations to their ordered applied/rejected outcomes; append/apply the gate. Gate READY requires that completed apply covers its gate entry, no pre-gate conflicting proposal remains, and every intersecting prepared transaction has resolved/finalized. Looking only at currently persisted locks is insufficient because a prior accepted prepare/write may still be in flight. Gates reject new intersecting PREPARE with a definitive negative vote; never park that prepare behind the gate. Existing tagged decision/FINALIZE/ABORT/recovery work is exempt from the gate so it can drain the state being fenced. If T is prepared at B while A is gated, T's prepare at A is rejected and its home decides ABORT (or completes an already-chosen COMMIT); recovery can propose ABORT while the home is still PREPARING. Thus the snapshot does not wait for B while holding A in a way that prevents T from terminating. New ordinary writes may be boundedly deferred or rejected. Conflicting snapshot attempts use no-wait retry; do not create a new deadlock graph.
3. After all gates are ready and no relevant prepared transaction remains, capture native snapshots at each group's ordered capture point. There is an interval with no writes to any scoped key; all images are therefore one consistent cut, including cross-group transaction effects. Do not release an early gate while another group is still resolving a transaction.
4. Persist the fence operation's completed/aborted outcome and release gates through replicated commands. A coordinator crash is recovered from this state; a participant never releases a still-active gate purely from its own timer. Native read pins can then live independently until their finite lease expires.

This trades a short scoped write pause for avoiding permanent MVCC overhead. It is appropriate for bounded interactive transactions and occasional long snapshot reads; it is not an O(1) global snapshot service for thousands of shards. Scope/participant/time budgets are explicit and admission rejects oversized snapshots. If measured workloads require frequent giant global snapshots, application-level MVCC is a separate product change with a quantified cost, not an invisible optimization.

A snapshot/cursor token contains cluster/database/column/schema identity, immutable bounds, direction, comparator/codec version, snapshot ID, pinned range lineage/generation, last emitted **full logical key** and authenticated expiry/generation data. Within a bucket it also identifies the exact logical member ordering; a hash key alone is not a continuation. Enforce exclusive `resumeAfter` in forward and reverse scans. Cursor bytes are opaque to applications.

Snapshot data is served from its actual retained native pins. A replica can keep a read-only pin through leadership loss while it remains alive and its generation remains valid; serving immutable pinned data requires the valid snapshot token, not new leadership. Do not assume another replica has the same RocksDB sequence or can reconstruct that snapshot. If the owner dies or its pin expires, return `SNAPSHOT_LOST`/`CURSOR_EXPIRED`. Never silently reopen at latest and skip/repeat records. A durable exported snapshot is the opt-in mechanism for failure-resumable long jobs.

Legacy autocommit pages remain independently consistent **per page**; a page spanning ranges uses a scoped consistent cut. Explicit transaction pages share their transaction snapshot. Existing retained streams get one consistent scoped snapshot and bounded retained-resource leases. A new explicitly named `READ_COMMITTED_RANGE` mode may walk current per-range snapshots with cheaper coordination; its documented concurrent-write semantics are not substituted into the legacy API. For a page confined to one group, avoid a multi-group fence entirely.

Execute range scans in comparator order, visiting only intersecting descriptors. Prefetch at most a small bounded number of successor ranges; no scatter to every shard for an ordinary prefix scan. Page byte/item budgets are global across all subrequests, not multiplied by shard count. A shard boundary is not end-of-data. `hasMore` must account for later nonempty ranges and retained pending items. First/last seek visits boundary ranges and skips empty ones; no full count is needed. Exact counts are an analytical operation at the declared snapshot, not a sum of unconstrained live estimates.

## 6. Catalogue, reconfiguration and movement

Run a small independent three-voter catalogue Raft group, optionally cohosted initially with dedicated resource reservations. It owns database/schema/operator manifests, node identities/capabilities, range descriptors, placement intents and cluster feature epoch. It is not queried for every operation. Loss of its quorum freezes topology/admin changes while healthy established data groups may continue with their already-installed ownership.

All administrative operations carry idempotency IDs, expected descriptor epoch and persisted stages. Catalogue intent alone is not write ownership. A data group enforces its installed range/schema epoch; the old group must commit its fence before a replacement can become writable. Cached redirects improve routing, not correctness. Explicit node incarnation and TLS identity prevent a wiped/reused node directory from masquerading as the previous replica. Bootstrap creates a unique cluster ID and an agreed initial membership; an empty node never elects itself into an existing cluster by guessing seeds.

### Replica relocation

Keep range/group identity stable. Add a nonvoting learner through Ratis's supported configuration workflow, stream a verified snapshot plus tail, verify operator/schema support and apply progress, then promote using the library's overlapping-majority reconfiguration. Transfer leadership if useful; remove the old voter only after the new configuration commits. No concurrent independent configuration change for a group. Never replace a majority at once or manufacture a smaller quorum after losing it. Rate-limit learner catch-up separately from ordinary replication; a slow learner must not fill unbounded queues.

### Split

1. Catalogue records a split intent with parent expected epoch, split key and new child identities. Split keys must be valid routing boundaries and never cut a physical bucket/colocation prefix.
2. Stop accepting new writable snapshots on the parent; drain/explicitly abort existing unprepared write transactions and finalize prepared ones. Commit `FREEZE_FOR_SPLIT` in the parent. It ceases all live writes at the frozen index. Immutable already-open read pins may finish within their leases.
3. **Normal online split uses the parent's existing replica/pool set.** Create both children from the frozen parent state by handing off ownership intervals without rewriting or scanning user keys. On each ready replica, sync the local WAL through the freeze and durably store both child seed/ownership markers, bound to the parent `(term,index)`, split operation and schema/epoch. Child groups start fenced, with new identities and agreed initial memberships; a replica cannot start/vote until its local seed is proven present. Seed creation is metadata work plus a durability barrier, not a full range export. The adapter must explicitly distinguish this already-present local seed from an installable remote snapshot. Keep parent recovery provenance/log references until durable child recovery/snapshot coverage is established. Prove this initialization with the actual Ratis adapter before using it.
4. Once durable child state and a child quorum exist, atomically publish the child descriptor pair in catalogue. Then commit child activation tied to that published transition. The parent remains permanently write-fenced; requests arriving at stale parent routes get a redirect/status result.
5. After activation, asynchronously rebalance children through the learner-relocation protocol; transfer data under the normal migration budget while they remain writable. Retire the parent group only after child activation, retained read pins, outstanding receipts/status and recovery references are safe. Keep a durable lineage/tombstone map so delayed operations are resolved rather than mistaken for new writes. A full-copy offline split variant may exist for recovery, but is explicitly unavailable for normal online split acceptance; never hold parent writes for a TB-scale remote export.

A crash between these stages may delay availability, but never creates two active writers or a coverage gap acknowledged as success. Before catalogue publication, an intent may be abandoned only through a committed parent unfreeze proving no child activated. After publication, complete recovery forward; do not casually resurrect the parent.

Receipts for a pre-split request may cover both children. Copy/reference all bounded unacknowledged parent receipts into the child bootstrap manifests and preserve the **original unsplit** operation ID/payload hash. A retry first resolves that original receipt through lineage. It must not invent two fresh subrequests and replay half a previously committed batch. Where no original receipt exists, the current router runs the original atomic operation through the multi-group path. Receipt GC/expired-session fences also transfer, so absence after GC is not permission to replay.

### Merge

Only adjacent ranges with compatible domain/schema/storage policy qualify. Relocate replicas to a common set first, while the ranges remain writable. Record one intent; fence both in canonical order after transaction drain; seed a new group over their already-local union with durable ownership markers; carry both lineage/receipt sets; atomically replace descriptors; activate the union and retire sources. No “copy then delete” shortcut or full data copy under the merge fence. Split/merge performance is accepted only after movement under live load and crash injection, not just empty ranges.

## 7. Checkpoints, recovery, backup, SST ingest and CDC

### Snapshot/install format

A range snapshot is an immutable manifest of its logical user data and all correctness metadata at one apply index: prepared plans/locks, receipts and GC fences, schema/operator digests, lineage, current Raft configuration and integrity hashes. Capture it in the group's completed-apply lane: finish the current batch, obtain one native RocksDB Snapshot before any later batch of that group, and read the applied marker and every user/internal CF through that same snapshot. Assert the marker matches the captured term/index and derive schema/config/ownership metadata from that cut, not a later live map. Keep the pin for the entire export. Capturing A and then scanning latest values can label n+1 data as n and duplicate a replayed merge; that is forbidden. Other disjoint groups in the shared pool may continue applying. Never compare replicas by SST filenames or RocksDB sequence numbers; those are replica-local. Logical data digest/export must canonicalize merge results and bucket order.

The portable baseline exporter walks a native snapshot in sorted order and creates canonical range SSTs (materialized logical values are acceptable at this infrequent boundary) plus metadata files. It avoids whole-database export when one range moves. Physical reuse of complete compatible SST files is a later optimization; clipped key ranges, tombstones, merge operands, sequence metadata and shared files make arbitrary file copying unsafe. This is not the existing raw-SST scan protocol.

Install into an inactive fenced interval. Stage files with checksums and expected range/epoch, fsync them and the manifest, then install while the interval remains unservable. If the JNI cannot atomically ingest all CFs and the replica marker, use a durable `INSTALLING(manifestId)` recovery state: delete/rebuild only that inactive interval and repeat from the immutable manifest after a crash. Publish the installed marker only after every required CF and metadata file is durably present; reopen/verify before serving. Never expose a partial multi-CF install. A conflicting active local owner aborts installation.

Use a checkpoint format that enumerates all volume/path IDs, WAL and metadata where physical checkpoints are used. Do not assume the existing multi-path layout is covered by stock Checkpoint. Portable range export avoids embedding host paths into cluster identity. Snapshot/log/state checksums detect corruption; a replica with an unverifiable committed prefix is removed from reads and repaired from a good quorum image. Automatic “skip corrupt records” is forbidden.

### Backups and restore

Backups are independently retained immutable data, not extra voters or hardlinks on the same failed disk. Capture a cluster-consistent backup using the scoped fence protocol across the selected database. Acquire the complete consistent-cut **native snapshot pins under the gates, then release the gates**; export and copy asynchronously from those exact pins. The write pause covers gate acquisition/transaction resolution/capture, not the data-sized export. Catalogue/schema/operator versions are pinned at the same cut and relevant unresolved decisions are resolved before capture. The backup is `IN_PROGRESS`, not durable or complete, until every export and the final manifest are durable in the backup destination. If a pin owner dies or a pin expires before its immutable export finishes, fail/restart that backup attempt; do not recapture one range at a new time and mix cuts. Admission bounds total pinned bytes, per-pool pin count/age, free-space reserve and export bandwidth. For a required failure-resumable backup, first persist each exact cut as a durable immutable range image while writes continue, then release that native pin; interruption before a particular image is complete still invalidates the attempt. Track a manifest graph with hashes, byte counts and required log tails.

Restore into a **new cluster identity** with fenced membership and fresh session epochs. Validate full manifest coverage and perform logical sample/full digest checks before traffic. Test restoration without access to original data directories. A one-range Raft snapshot proves replica recovery, not disaster backup. Asynchronous cross-site backup has an explicit RPO; synchronous regional quorum is a separate latency/cost policy. Quorum loss never triggers an automatic force-recovery that can discard acknowledged writes.

### Large writes and SST ingestion

Ordinary atomic entries have explicit encoded-byte and mutation-count limits. Reuse current `LATENCY` limits (256 items/2 MiB) and page limits (4,096 items/8 MiB) as source contracts; publish distributed participant/transaction limits separately. Reject oversize atomic operations before effects. A streaming bulk API has explicit chunk IDs and per-chunk receipts/partial-progress reporting; it is not an infinite atomic transaction. Fixed multi operations that claim atomicity use one-group batches or multi-group commit.

For large file ingest, use Ratis's released state-machine data/stream hooks, **after an integration test proves their exact durability ordering**. Replicate an immutable manifest reference in the log and ensure a voter counts the entry durable only once its referenced bytes, checksum and directory entry are durable. Implement `DataApi.write/link/flush/read/truncate` and reference lifetimes; the no-op defaults are unsafe for this use. Missing files prevent apply/serving and trigger fetch/repair. Log/snapshot retention protects every referenced file until no recovery/CDC/backup consumer needs it. [R4]

Live atomic SST ingestion needs a crash-recoverable publication boundary with the applied index. `ingestExternalFile` followed by a separate index write is not atomic and replaying a merge SST is not harmless. The first supported bulk SST workflow therefore ingests into **new fenced ranges**, then activates them through the catalogue protocol. Live overlapping SST ingest remains `UNSUPPORTED_DISTRIBUTED_INGEST_MODE` until an atomic native multi-CF ingest+metadata mechanism or an equally rigorous generation-swap protocol is implemented and fault-tested. Ordinary replicated logical bulk writes remain available for live updates. Existing multi-path path-ID restrictions remain enforced.

`*_NO_WAL` modes cannot request acknowledged nondurable distributed data; reject them explicitly in distributed mode. `SST_INGEST_BEHIND` and merge-ingest-behind have no implicit distributed translation. Physical compaction remains local replica maintenance with local tokens; it never determines logical transaction order.

### CDC

Distributed CDC is derived from committed canonical commands/finalized effects, not the local RocksDB WAL. A cursor is `(range lineage, log index, mutation ordinal)`; a subscription covering several ranges has a vector/checkpoint map. There is per-range order and explicit transaction ID/decision metadata, not an invented global scalar order. Consumers needing transaction-atomic output buffer a bounded transaction envelope or use a committed-transaction subscription. Normal CDC never emits prepared-but-aborted plans.

Include PUT, DELETE, MERGE, explicit range-deletion events and topology lineage barriers in the new format. An operand event stays an operand; a resolved-value CDC option must define its at-commit image and associated cost rather than reading an arbitrarily newer value. Persist subscription acknowledgements idempotently in protected CDC storage. Retention is bounded in bytes/age; if a consumer falls behind, return a gap requiring snapshot+tail resynchronization. Do not pin Raft logs or SSTs without limit to satisfy an abandoned consumer.

Legacy scalar CDC is valid for standalone/single-group capability only. On a distributed multi-group database, reject creation/poll with `CDC_CURSOR_VERSION_REQUIRED`; do not pack shard IDs into a `long` and falsely preserve total order. Preserve old API behavior in standalone mode and add parity tests for the explicitly supported new Java/gRPC/Rust/Thrift surfaces.

### Existing raw-scan migration

Physical SST names are local to a database incarnation and can disappear under compaction. Keep existing standalone `scanRawResumable` semantics; distributed connections must reject the old unqualified physical tokens. Provide a durable **export job** pinned to an immutable source snapshot/coverage generation, with chunk identities `(jobId, rangeLineage, snapshotIndex, ordinal, contentHash)`, complete coverage metadata, final-chunk completion after native reader close, and acknowledged progress only after destination writes succeed.

A shard split during an export either waits for its finite pin or leaves the immutable source export available; it cannot silently remap an acknowledged filename to new contents. The identified Yotsuba migration must explicitly adopt this protocol before being declared compatible with a distributed source. Final Rockserver acceptance includes the same write-before-ack/barrier/restart workflow using a representative consumer fixture.

## 8. Scheduling, networking and native ownership

Extend the existing workload scheduler, not a parallel unbounded executor universe. Admission budgets exist per node, pool, tenant/workload and range. Count queued **bytes**, entries, oldest age, in-flight log bytes, prepared bytes, native snapshot age/bytes, response retention and replica catch-up separately. The sum of accepted work must fit a published resource budget. Tenant labels/operation IDs must not become unbounded metrics labels.

Client profiles keep their present meaning. Internal Raft heartbeat/vote/read-index/configuration traffic, transaction decisions/finalization and release operations have reserved threads/queues/network capacity. Control payload size is bounded so clients cannot disguise bulk data as control. Log payload replication still consumes data bandwidth. Committed apply cannot be rejected as if it were new user work: reserve its capacity at proposal admission, throttle new writes from lag/pressure, and keep enough drain capacity to reach a stable state. A stalled CF cannot consume every control worker.

Use deadline-aware bounded batching: byte/item ceilings plus a short maximum delay; never hold latency traffic waiting for a bulk batch. DRR/weighted scheduling across active groups prevents a hot range monopolizing the pool; preserve deliberate profile guarantees. Yield range work at existing item/byte/time quanta. Propagate only remaining deadline duration across hops. Replication and cleanup completing committed work outlive a caller deadline where correctness requires it.

Measure and limit foreground writes, compaction bytes/CPU, flush bandwidth, snapshot export/import, learner catch-up, backup and analytical scan concurrency as distinct budgets. Use compaction debt, WAL growth, device latency, disk reserve and foreground p95/p99 as pressure signals. Background maintenance needs minimum progress so foreground protection does not accumulate an eventual stall. Pause/reduce migration first under pressure, and do not schedule expensive compaction on all replicas of a hot group simultaneously. Replica placement/read routing can account for compaction health only within the promised consistency mode. HATS supports considering these jointly, but its Cassandra policy is not copied blindly into Raft. [P6]

Use existing gRPC/Netty client transport first and Ratis's supported transport internally. Maintain pooled long-lived channels keyed by node identity, not one connection per request/range. Serialize a canonical command once; avoid decode/re-encode per forwarding/replication hop where the APIs permit safe buffer retention. Batch small operations; use large-file streaming only for large data. Compression is thresholded and measured; do not compress tiny already-compressed operands by default. TLS and authentication are included in the benchmark, not removed to obtain a flattering throughput number.

Do not claim end-to-end zero copy: Java protobuf, gRPC, Ratis log buffers, checksums, TLS and JNI each have actual lifetimes/copies. Instrument allocation and retained direct bytes. Ratis's reference-counted data channel requires balanced retain/release after asynchronous use; existing FFM merge inputs cannot escape their callbacks. Native direct-get/iterator views must be retained or copied before an async boundary according to their real contracts.

Ownership chain: node/pool -> range replica -> native CF/operator -> request/transaction/snapshot/iterator -> retained output buffer. Cancellation stops new admissions/demand and may cancel unsubmitted proposals. Once a proposal could have committed, cancellation abandons the waiter and leaves status/recovery ownership with the range. JNI work retains its leases until it actually returns; interrupting a future does not permit closing the CF, arena or database.

Shutdown: stop new client ownership; transfer leaders if quorum permits; settle/reject queued unsubmitted work; persist/reconcile admitted log work; drive transaction decisions or leave durable prepared state recoverable; drain native calls and release snapshots/iterators; close operator arenas/CFs/pools only after their users stop. A drain timeout reports incomplete drain and retains necessary native ownership, rather than freeing resources under active JNI. Do not wait for an executor to terminate from its own callback.

## 9. Resource and amplification model

Keep a baseline/candidate ledger for each workload, not a single “ops/s” number. Let `E` be canonical command bytes per accepted request, `W` local applied RocksDB batch bytes (user operations plus receipts/metadata), `r` replication factor, `a` measured SST write amplification, `Q` number of keys changed while the oldest unprepared snapshot remains live, and `L` retained snapshot age.

Ignoring headers/compression, the leader sends about `(r-1)E` replication bytes. The cluster appends about `rE` Raft-log bytes, `rW` local-WAL bytes and `r*a*W_user` SST/compaction bytes. Actual device bytes, fsync group size, metadata amplification and replicas lag must be measured. For a sparse update, `E` contains operand bytes; replacing it with a full value of size `V` increases replication by approximately `(r-1)(V-operandBytes)` per update before compression. That is why merge preservation matters.

Dedup has fixed envelope/result overhead. For tiny key-only writes, that overhead may exceed the user payload. Amortize it with bounded multi/bulk batches and client acknowledgement watermarks; do not remove it by calling unsafe retries “idempotent.” Outstanding receipt storage is roughly accepted rate times unresolved/acknowledgement window times average receipt bytes, plus a bounded session-fence index. Returned previous values can dominate this budget.

The transient conflict index costs approximately `Q*(physicalKeyBytes + index/flags + data-structure overhead)` plus interval entries. With sustained optimistic transactions it may be active continuously; assume this in benchmarks. Use packed/arena-backed structures where measurements justify them, not a heap object per write. No persistent per-write stamp CF is in this design. A permanent 8–16-byte version payload plus repeated keys and its own LSM compactions can materially inflate key-only storage; full application MVCC additionally retains historical values and complicates native merge resolution. Native snapshots already pin old SST versions for `L`, so bound lifetime/bytes regardless.

The transaction cost is validation/history CPU, native snapshot retention, conflict retries, and, across groups, prepare + decision + finalization rounds. For disjoint one-group transactions, pipeline depth `p` and batch size `b` must permit approximately `p*b/RTT` in-flight completion capacity; actual CPU/disk/transport may be lower. A single hot key remains serialized. Report useful **committed unique work**, abort/retry amplification and client-observed latency, not attempts or Raft append rate.

Keep Raft logs, RocksDB WAL/internal correctness metadata, mutable upper levels and latency-critical data on durable fast storage. Use HDD for cold lower levels where observed access patterns justify it, with existing path-ID semantics and sufficient transient free space for compaction, snapshots and one repair/movement. Do not assume every lower-level key is cold. Preserve isolated named caches and partitioned filters where supported. Bloom/Ribbon, compression levels, BlobDB thresholds and direct I/O are per-column measured choices, not distribution requirements.

CPU/NUMA model: record actual sockets, physical cores/SMT, DDR generation/speed, affinity and first-touch placement. A pool's apply workers, direct buffers and cache shards should normally share locality; shard mutable counters and avoid a global hot atomic on every operation. Use spare cores only when device bandwidth/remote-memory effects justify it. Dedicated process/pool separation may outperform heroic cross-socket sharing. No claim is accepted from desktop-only results for a DDR4/NUMA deployment.

For large values, native BlobDB/KV separation is an optional measured optimization; scan locality, partial-update materialization and garbage-collection amplification can erase its benefit. Disaggregated shared storage/erasure-coded cold SSTs can lower replication cost at scale but adds another consistency/fencing/GC subsystem and network I/O on reads/compaction. It is deferred from the default local-storage design. [P5, P7–P8]

## 11. Failure invariants and decisive validation

The adapter/protocol state machines must be small enough to model. Use deterministic schedulers and a small model (TLA+/PlusCal or equivalent executable exhaustive state model) for proposal reservations, transaction prepare/decision/finalize, snapshot fencing and split activation. Raft library tests do not prove their composition. Then use actual multiprocess Rockserver/Ratis/RocksDB with network and disk fault injection; a simulated cluster alone is insufficient.

| Invariant / fault | Required observable result |
|---|---|
| Minority partition, stale leader, delayed messages, reused node ID | At most one writable owner; no linearizable read from an isolated stale leader. Wrong cluster/incarnation/epoch rejected. |
| Crash before/after quorum, after local apply, before reply, repeated merge request | Acknowledged writes survive any one voter loss; retry returns one original result and exactly one logical effect. Unknown result is resolved explicitly. |
| RocksDB metadata CF flush before data CF; torn local WAL/log tail; crash at snapshot publication | No marker skips lost business data and no replay duplicates a merge. Test with real WAL enabled; any WAL-less experiment repeats these with atomic-flush instrumentation. |
| Async apply futures completing out of order | `A` is contiguous completed state; strong reads/receipts cannot overtake missing work. |
| ABA, absent-key create/delete, range phantom, range delete, bucket collision | Snapshot transaction conflicts when any protected physical key/predicate changed, regardless of equal final bytes. |
| Disjoint concurrent transactions | Multiple proposals remain in flight; no unnecessary shard-wide quorum drain. Throughput is not RTT-limited at depth one. |
| Leader change after validation/before append/after append; inherited uncommitted prepare | No unvalidated interposition; unprepared handles fail; inherited committed locks restored before admissions. |
| Coordinator crash, prepared participant restart, delayed ABORT/COMMIT, decision committed before one apply | Exactly one decision; readers wait/help rather than see fractured atomic state; prepared locks survive until resolution. |
| Snapshot fence racing multi-group commit or split; coordinator dies after first gate | Snapshot is a consistent cut or fails explicitly; gates recover; no unilateral unsafe release or permanent forgotten fence. |
| Split/merge/relocation crash at every persisted stage | Coverage and one-writer ownership hold; original operation receipts remain discoverable; bucket/prefix boundaries stay intact. |
| Cursor pause, cancellation, expiration, owner restart, topology movement | Bounds/order/global page budget hold; immutable snapshot continues only with a real pin; lost snapshot is not silently replaced. |
| Corrupt/missing bulk file, operator jar mismatch, partial multi-CF import | Replica stays fenced and repairs; no acknowledged activation of partial data. |
| CDC lag/gap, split lineage, transaction retry, range delete | No prepared events or silent gap; replay dedup/checkpoint and topology barrier give complete declared coverage. |
| Full disk, fsync stalls, slow learner, compaction/migration storm | Bounded admitted bytes and reserved control/finalization progress; no unbounded queue or fake success. |
| Cancel/shutdown while JNI/FFM callback blocked | Native leases survive until return, release once, and no arena/CF is closed underneath active work. |

Keep a reference logical state machine that includes arbitrary **noncommutative** merge operands, previous-value results, collisions, ranges and transaction outcomes. Compare all live replicas by logical state at a quiescent barrier. Linearizability checking covers point/atomic operations; transaction history checking covers serializability/write skew/phantoms and fractured reads. Crash tests must include process kill and storage fault/power-loss simulation; `kill -9` alone does not erase an OS page cache or test fsync claims.

Representative early workflow: three independent server processes, real client routing, two columns in a colocated domain; perform a conditional update plus a noncommutative merge, request previous/merged result, drop its reply, kill the leader, retry the same identity, verify one effect, scan in both directions, restart the failed node and compare state. Immediately extend to a second group and the four-column monitor/fence transaction fixture. No mocked Raft or in-process map counts as this milestone.

### Equal-durability performance acceptance

Build baseline/candidate from immutable SHAs in isolated worktrees and record artifacts/configuration/JDK/JNI/OS/hardware. Preserve the repository's existing standalone performance contracts where relevant (`docs/v1.3.11-performance-contract.md`, pressure and mixed-workload suites). They are historical contracts with a named baseline, not permission to substitute async local writes for quorum durability.

Use three comparisons: (1) unchanged standalone versus candidate standalone, same durability/config; (2) one-group distributed candidate versus a recorded quorum-durable implementation baseline, identical replicas/ack conditions, to measure adapter/batching improvements; (3) increasing nodes/ranges under the same consistency/durability to show scaling, including bytes and cost. A single-node `sync=false` RocksDB run is an explanatory lower bound, not an equal-durability competitor. No numerical speedup is promised by this document.

Predeclare one primary outcome and protected p95/p99, memory, GC/allocation, disk/NIC, correctness and recovery bounds for each workload. Use counterbalanced paired runs, sufficient warmup/LSM turnover, repeated samples and confidence intervals, including sustained steady state and cold starts. Retain raw results and unique committed-operation conservation. Set the concrete hardware-dependent targets before the tuning campaign; publish FAIL if they are missed rather than weakening quorum or discarding failing samples.

Required separate workloads: tiny key-only membership/presence; heterogeneous message values and sparse patch/merge ratios; monitor-style conditional four-column transactions; hot-prefix/skew/collisions; first/last and bounded pages; retained forward/reverse scans; large logical bulk writes and new-range SST import; CDC tailing; mixed seven-profile operation under compaction, one failed replica and migration. Archive datasets must exceed RAM and exercise HDD capacity/fast upper tiers where that is the intended deployment; do not substitute the membership dataset.

Measure: useful throughput and p50/p95/p99, end-to-end/queue/quorum/apply stages, retry/abort rate, proposal pipeline occupancy, fsync group sizes/latency, log/apply lag, CPU cycles and allocation per useful mutation, heap/direct/native/RSS, thread/FD counts, remote NUMA/cache behavior where available, NIC bytes, logical/local WAL/Raft/SST/device bytes, read/space amplification, cache occupancy and compaction debt. Include resource return to baseline after repeated cancellation, reconnect, split/move and restart.

Report a supported envelope: maximum tested group density, participants/transaction bytes, snapshot lifetime/bytes, bulk chunk/file size, retention windows, repair rate and safe free-space reserve. Lack of representative hardware is a named performance-acceptance blocker, not proof from a desktop smoke run.

## 12. Implementation sequence and completion definition

Use the new isolated `codex/` worktree/branch from the verified base. Preserve the main checkout and unrelated GUI changes. Commit coherent, reviewed stages there. The user intends to merge at the end; neither final merge nor production rollout is authorized by completing this design.

1. **Freeze contracts and verify the integration seam.** Add distributed capability/error/envelope types; isolate native batch apply and completed-index accounting while keeping standalone behavior. Pin Ratis and run a real three-process group with durable log, restart and current-term linearizable read. Measure idle per-group cost at useful densities now. Document the selected dependency and storage-mode facts from actual tests.
2. **One real replicated workflow.** Implement durable receipts/session fences, pure immutable-operator merge admission, ordered apply, response-loss retry and the early workflow above over gRPC. Include actual snapshot recovery to a fresh node. This is the first vertical slice, not the end goal.
3. **Routing, multiple groups and scoped transactions.** Implement catalogue/bootstrap, range routing, native snapshots/history, bounded reservations and **disjoint pipelining**, single-group transactional compatibility, then durable status groups/2PC and scoped snapshot fences. Run the four-column/fence fixtures under failures before adding more features. Preserve false/conflict versus unknown commit and reject unsupported scopes explicitly.
4. **Elasticity and operational recovery.** Implement learner relocation, split/merge staged fencing/activation, lineage-aware receipts, schema/operator distribution, repair and consistent backup/restore. Exercise nonempty ranges under active writes/reads and kill every stage. No static shard map as a final deliverable.
5. **Long workflows and transport parity.** Implement strict pages/streams/cursor pin loss, durable export jobs, new-range SST ingest with proven file durability, distributed CDC vector cursors/transaction envelopes and consumer compatibility fixtures. Preserve existing standalone modes; reject distributed physical/scalar modes honestly. Update public clients/protocol fixtures and capabilities reporting together.
6. **Resource and performance completion.** Finish bounded admission/control isolation, compaction/catch-up budgets and JNI drain tests; run the equal-durability suites at representative density/size, tune from profiles, validate multi-node scaling, failure recovery and backup restoration. Remove the early global-drain bottleneck. Only then prepare the branch for the user's final review/merge decision.

This distributed product is unreleased. Maintain one current wire and storage encoding per artifact and change it directly as the design evolves. Operation kinds, schema/operator identities, directory generations and Raft/configuration epochs remain explicit correctness inputs; they are not protocol releases. Do not preserve intermediate checkpoint encodings or add migration readers, dual query modes or rolling-feature activation gates. Existing standalone API/storage contracts and compatibility with pinned third-party libraries remain required.

**Done means** real independent nodes survive leader loss and restart; acknowledge only durable quorum writes; preserve ordered sparse merge/conditional semantics and cross-column atomicity; route and rebalance nonempty data with dynamic splits, merges and relocation; offer bounded honest read/snapshot/export/CDC contracts; restore a verified backup into a new cluster; pass deterministic/fault tests and report representative equal-durability performance with all resource limits. A design, a mock cluster, static partitioning, replication-only demo, passing unit count, commit or push is not completion. If a required capability or hardware gate remains unresolved, keep the implementation task active and report that precise gap instead of declaring distribution finished.

## Handoff boundaries

No source files were edited or compiled for this design. Canonical design and consumer evidence are staged outside the dirty checkout for the coordinator to place into the new task's worktree. The implementation must inspect exact current API signatures before editing and verify its branch/base. Existing standalone local-RocksDB semantics remain authoritative unless this document explicitly names a distributed capability restriction. Any discovered inconsistency in the proposed protocols is a reason to amend the design with evidence before implementing that stage, not to quietly weaken durability, atomicity or retries.
